## Ranked confirmed defects and minimal plans

**Must-fix before relying on these workflows:** IA-1, IA-2 and IA-3 (paid-work outcomes/ownership and company boundary), IA-4 (shared edit loss), IA-7 (destructive crop correctness), and IA-8 (draft loss). **Workflow candidates for the next polish batch:** IA-5 and IA-6; both are confirmed defects, with lower urgency. ### IA-1 — P1: AI reports Done after all or some outputs fail to persist

- **Trigger:** A successful generation reaches result handling, but disk is full, the gallery DB insert fails, or one output download fails. The same handler runs product and folder batches.
- **Result:** Each per-output error is logged and swallowed, then the task unconditionally becomes `done`, progress 1, with no error. All failures produce zero gallery images; partial failures silently produce fewer than requested. Auto-add/promotion and export-copy failures are also stderr-only, so a completed generation can miss requested follow-on work.
- **Root cause / exact lines:** `main/ai/queueRunner.js:235–347`, especially per-output catch at 333–335 and unconditional Done at 339–346; auto-attach catch at 310–312 and export catch at 329–331. The empty-output guard at 179–190 protects only the provider's empty array, not local persistence. `renderer/modules/AIStudio/index.jsx:959–973` labels zero-result tasks "Done · no images" and offers Repair; partial loss remains hidden.
- **Evidence:** Memory-only VM execution with `writeFile` rejecting `ENOSPC`: `status=done`, gallery row count=0. Existing tests cover renderer geometry and workspace saves, not this result handler.
- **Minimal steps:** Count durable gallery successes and collect actual errors; mark zero persisted results failed and expose partial completion in the existing task error/message presentation. Record usage/cost even when local filing fails. Report auto-attach/export problems as follow-on warnings while keeping successfully saved gallery images. Correct "Repair to re-fetch" copy: Repair re-submits a paid generation; it does not recover the same result. Do not introduce automatic paid retries or a release-wide generation lock.
- **Acceptance:** Stub two outputs: both fail, then one succeeds/one fails; assert status/error, actual cost and gallery count match. Stub image cap and export permission denial; the saved image remains available and the requested follow-on failure is visible. Happy path remains Done.
- **Dependency / effort:** Independent; existing task fields + queue UI; **M**. Persistent byte recovery beyond the existing in-memory result would require separate product direction and is not part of this plan.

### IA-2 — P1: Cancel and Repair lose ownership of a still-running provider request

- **Trigger:** Cancel an active AI task, enqueue more work, or immediately Repair the cancelled task / a task shown as running for five minutes.
- **Result:** Cancel removes the ID from the concurrency set although the request is still running; new paid calls can exceed the configured limit. A late rejection changes Cancelled to Failed. Repair also removes the live ID and requeues the same task, so the old and new submissions can write to the same task and per-product filenames. A cancelled task can become Done if Repair resets its status before the original result returns. Cancellation during asynchronous filing has no further status check after the initial onDone check.
- **Root cause / exact lines:** `main/ai/queueRunner.js:79–85` counts `inflight.size`; 153–165 owns the still-active promise; 175–177 checks cancellation only once; 358–366 overwrites a cancelled status on failure; 485–496 Repair unconditionally requeues and deletes its slot; 522–528 Cancel deletes the slot. UI exposes Repair for cancelled/long-running tasks at `renderer/modules/AIStudio/index.jsx:965–968,1045–1058`.
- **Evidence:** VM execution confirms Cancel frees its occupied slot, a late failure changes Cancelled→Failed, and Repair accepts/requeues an in-flight task ID.
- **Minimal steps:** Keep provider slots until the actual promise settles (release centrally in `finally`). Refuse Repair while that ID has an active promise; retain explicit Queue fresh as a separately identified new task. Preserve Cancelled in the failure path and recheck cancellation/removal at filing boundaries before attachment/final completion. Clarify in existing cancellation copy that stopping acceptance of results cannot undo provider charges. If cancellation arrives during an already-started file write, that write may complete; preserve those bytes and suppress subsequent gallery/auto-attach actions after the check. Do not erase already-saved gallery results or undo an attachment that completed before cancellation. Avoid global locks.
- **Acceptance:** Deferred provider stub with concurrency=1: cancel task A, queue B, and verify B starts only after A settles. A result arriving after cancellation starts no gallery/attachment work; a late failure cannot change Cancelled to Failed. Inject cancellation at write completion and before auto-attach: no later variant/attachment/final Done runs, while already-saved bytes/results remain. Repair A while live must return an actionable error. Repair after settlement creates only one active submission, within the limit.
- **Dependency / effort:** Implement before broad AI retry/result changes; same runner lifecycle as IA-1; **M**.

### IA-3 — P1: Bulk gallery promotion lacks source-company authorization

- **Trigger:** Promote an unassigned gallery entry from company B while company A is active, through a stale UI or RPC request carrying B's gallery ID and A's destination product.
- **Result:** B's image bytes are imported into A's product and the gallery row is attached there. Unlike favorite/delete/export handlers, promotion validates only the destination product. New-product creation can happen before source ownership is checked.
- **Root cause / exact lines:** `main/ipc/ai.js:228–252` reads `entry` and resolves/creates destination without checking `entry.companyId`; imports at 256–265 and attaches at 286–288. Compare the existing source authorization in favorite at 189–195 and delete at 197–201. Templates being global is intentional; AI gallery rows are company-scoped.
- **Evidence:** VM registered the real handler with company A active, an unassigned gallery row owned by B, and A's product; import and attach both executed. This proves handler behavior, not network or visual exploitation.
- **Minimal steps:** Immediately after loading the gallery entry, use the same source ownership checks as favorite/delete, before any product creation or file access. Keep destination authorization. Reuse an existing shared helper if appropriate; no new auth framework.
- **Acceptance:** Native isolated fixture with A/B: foreign bulk gallery→A product and foreign bulk gallery→new product both reject with zero import/create/attach side effects; same-company bulk and per-product promotions still work. Validate standalone and RPC entry paths.
- **Dependency / effort:** Independent, trust-boundary fix; **S**.

### IA-4 — P1: Overlay templates silently overwrite concurrent edits

- **Trigger:** Two Macs open the same shared overlay template. A saves a new layout; B changes its stale template name, then autosave sends B's entire stale layout.
- **Result:** B's save replaces A's elements/inset/tags without a conflict. Within one editor multiple saves are also allowed in flight, and an older acknowledgment can mark a newer draft saved. Done/back do not wait for save success; a failed write can leave only an unmounted editor's draft.
- **Root cause / exact lines:** `renderer/modules/OverlayStudio/TemplateEditor.jsx:332–375` implements independent snapshot saves with no serialized queue or revision; 359–367 sends all fields, 368–369 accepts any acknowledgment as current. `main/ipc/templates.js:300` forwards unconditionally; `main/db/imageTemplates.js:107–120` updates `WHERE id=@id` only. Done/back call onClose directly at TemplateEditor 474,510 and `renderer/modules/OverlayStudio/index.jsx:121` unmounts immediately. Catalog/Social/Label revision handling and `renderer/lib/latestSaveQueue.js` already exist; Overlay is absent from `test/editorConcurrency.test.js`'s registered domains.
- **Evidence:** Source-confirmed unconditional full-snapshot overwrite. Concurrent save ordering was not exercised on two Macs; the missing revision condition itself is unambiguous.
- **Minimal steps:** Extend existing revision-aware save/conflict flow to global image templates using their existing updatedAt version, and serialize saves through createLatestSaveQueue. Advance acknowledgment only for the saved draft; retain a newer draft. Flush before Done/back/Apply and block those transitions on failure with existing conflict choices. Register the company-switch flusher where applicable. No schema-version bump.
- **Acceptance:** Native two-client stale snapshot test preserves A's change and returns conflict to B. Renderer deferred saves test verifies latest draft and status. Done/back must wait and stay in editor on a failure; changing to another template cannot let an old response repaint it.
- **Dependency / effort:** Reuse latestSaveQueue/ConflictModal and the existing optimistic DB update helper; precedes IA-5; **M**.

### IA-5 — P2: Overlay editor Apply can run a different template or an older draft

- **Trigger:** Edit a template that is not first in the list, click Apply immediately, and accept the modal's default.
- **Result:** The modal is not told the editor's template ID. It independently defaults to the first returned template, or retains a previously selected ID. It fetches saved templates and the runner loads the saved version, although the canvas preview uses the current inline draft. Thus the Apply action described as "this template" can produce another template or an older design.
- **Root cause / exact lines:** `renderer/modules/OverlayStudio/TemplateEditor.jsx:503–509` opens directly; 805–810 passes productIds but no template ID. `renderer/modules/ProductLibrary/BulkOverlayRunModal.jsx:57–58,89–98` chooses the first template only when its own ID is empty; 169–175 submits that local ID. `main/ipc/templates.js:441,494,571` fetches by saved ID. EditorCanvas's preview passes the inline current draft at `renderer/modules/OverlayStudio/EditorCanvas.jsx:209–217`.
- **Evidence:** Source-confirmed prop/state/handler mismatch. This is not the already-fixed phone viewer position-preview bug.
- **Minimal steps:** Add an optional initialTemplateId to the existing modal and explicitly reset its selection when opened from the editor. Flush the editor draft successfully before opening it; use the saved acknowledgment. Retain the current modal structure and its Library defaults. Optionally keep the template select available if deliberate switching is useful, with current template preselected.
- **Acceptance:** Edit template B with template A newer in list; Apply defaults B, and immediate Apply includes the last edit. Failed save opens no run modal. Library bulk Apply retains existing behavior; reopening editor Apply does not reuse an unrelated prior template.
- **Dependency / effort:** IA-4 provides reliable flush; small prop change, **S** after IA-4. Does not restructure the closed bulk modal.

### IA-6 — P2: Overlay Undo fails to restore a whole drag and loses the next edit checkpoint

- **Trigger:** Drag/resize continuously, then Undo; or Undo and make a new edit.
- **Result:** A drag burst 0→1→2→3 stores 2 as its prior snapshot, so Undo restores only the last intermediate move. Undo/Redo sets skipNextCommitRef=true but calls setTemplate directly rather than scheduleHistoryCommit; consequently the first normal edit afterwards consumes that flag and receives no checkpoint. An uncompleted history timer can also commit after Undo.
- **Root cause / exact lines:** `renderer/modules/OverlayStudio/TemplateEditor.jsx:229–247` clears the previous timer and captures every newest prevState instead of the burst-start state. Undo/Redo 250–271 set a skip flag and bypass the function that clears it. These are separate from the fixed stale keyboard-listener bug at 421–467.
- **Evidence:** Executed extracted real history functions with fake timers: burst Undo returned state 2, and first subsequent edit scheduled no history timer.
- **Minimal steps:** Capture the first pre-edit snapshot of a burst until it settles; flush/cancel the pending history checkpoint before Undo/Redo. Remove the unused skip mechanism or consume it during the navigation path. Keep the existing 50-entry session-only history and do not add a history library.
- **Acceptance:** Pointer burst and text burst each Undo to the state before the entire burst; two completed gestures have two checkpoints. Undo→new edit invalidates redo and its own Undo works. Immediate Undo during the 300ms timer behaves consistently. Keyboard and toolbar use the same action.
- **Dependency / effort:** Independent of persistence, **S**.

### IA-7 — P1: Image crop previews and saved crops use different coordinate systems

- **Trigger:** Import a non-square source (e.g. 4000×2000), use the default square processing canvas, choose a 1:1 crop, and Apply. Rotation and an already-processed image amplify the mismatch; Overwrite source makes it destructive.
- **Result:** The square-looking selection can produce a 2:1 crop, and image placement/selected pixels need not match the output. The crop overlay spans the full processing canvas while the raw photo is contained/letterboxed. When processedFilepath exists, the screen still shows the processed image while IPC crops raw source. The renderer applies settings.rotation visually, but crop IPC sends only straighten.
- **Root cause / exact lines:** `renderer/modules/ImageWorkspace/CanvasView.jsx:28–35,219–224` derives normalized aspect from processing canvas dimensions; 232–239 and 269–273 normalize pointer coordinates against full crop overlay; canvas shape at 294,319. CSS `renderer/index.css:6215–6218` uses object-fit contain. Raw rotation/processed display at CanvasView 327–363. `renderer/modules/ImageWorkspace/index.jsx:174–183` sends this rectangle plus straighten only. `main/ipc/images.js:639–651,681–686` interprets those fractions against raw source or its post-straighten dimensions.
- **Evidence:** Real extracted rectAspectFromOutput helper + IPC math: equal 0.5 fractions for a 1:1 selection on 2000² canvas produce 2000×1000 from a 4000×2000 source. No actual customer image was altered.
- **Minimal steps:** Give crop mode a dedicated display of the same source and transformed dimensions used by crop IPC. Normalize drag/ratio against that displayed image rectangle, with letterbox offsets excluded. Decide rotation handling by following current preview intent: thread the existing workspace rotation into the source transform before straighten, or make the crop view explicitly raw and do not display that transform. Reuse cropPreview for authoritative verification instead of adding a second crop engine. Preserve overwrite confirmation and immutable replacement guards.
- **Acceptance:** Isolated landscape/portrait fixture with marked corners: 1:1 and 4:3 selections produce correct output ratio and exact selected pixels; compare cropped preview to saved bytes for raw/processed, 90° rotation and straighten. Both new-copy and overwrite destinations must agree. Native image checks + rendered UI inspection required.
- **Dependency / effort:** Existing cropPreview/reframe helpers; **M**, largest item in this area because preview geometry must be verified.

### IA-8 — P2: Completing a crop clears the newly selected image's edits

- **Trigger:** Start Apply crop for product/image A, switch to B while IPC is pending, and adjust B's crop before A completes.
- **Result:** A's success clears the component's current cropRect and cropStraighten before checking which product is now active. That is B's state and can autosave the cleared values onto B. Switching images within the same product also passes the product-only guard.
- **Root cause / exact lines:** `renderer/modules/ImageWorkspace/index.jsx:143–183` captures A; 185–186 unconditionally mutate current settings/crop mode, then the product guard occurs only after refresh at 187–188. Product navigation is busy only when `processing` is true at 811–815, but cropping sets a separate cropApplying flag at 151. ImageStrip selection 762–802 has no crop lock. Existing isCurrentContext with immutable identity + generation is available at 245–249.
- **Evidence:** Executed extracted handleApplyCrop with deferred API result: A completes after activeProductIdRef becomes B; B's cropRect becomes null and cropStraighten becomes 0.
- **Minimal steps:** Capture editor context/generation when crop begins and guard settings/mode mutations using existing isCurrentContext before any setSettings. Refresh A's saved results through existing stale-safe store methods; do not repaint/alter B. Include cropApplying in operation guards to prevent concurrent same-image flip/process/crop; decide whether navigation remains allowed, but retain identity guards either way.
- **Acceptance:** Deferred crop for A, switch to B or another image in A, edit its crop: old completion leaves new crop unchanged and no cleared payload saves to new image. Successful crop on still-active A clears only A. Failed crop does not erase draft.
- **Dependency / effort:** Shares crop handler with IA-7 but can land independently first; **S**.
